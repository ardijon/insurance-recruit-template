# راهنمای گردش‌کار: Graphify + مهندسی قوانین برای OpenCode

این بسته، بر پایه سه منبعی که برام گذاشتی (ویدیوهای محمد دهدار و مخزن گیت‌هاب
`Graphify-Labs/graphify`) ساخته شده و با ساختار فعلی پروژه‌ی تو (`AGENTS.md`،
پوینترهای `CLAUDE.md`/`GEMINI.md`، و `.agents/skills/<name>/`) ترکیب شده.

## هدف

سه چیز هم‌زمان:

1. **کاهش مصرف توکن** — با جایگزین کردن جستجوی تکراری فایل‌ها با یک گراف دانش
   محلی که ایجنت مستقیم به گره مورد نظر پرش می‌کنه.
2. **ساختارمندتر و حرفه‌ای‌تر شدن** — با جداسازی «قوانین استراتژیک» (`edge.md`)
   از «استانداردهای بصری» (`design.md`) و «پرامپت‌های عملیاتی» (`prompts/`).
3. **بدون تغییر ظاهر نرم‌افزار نهایی** — این نکته مهم‌ترین بخششه، پایین توضیح دادم.

## چرا ظاهر نرم‌افزار تغییر نمی‌کنه

`design.md` دقیقاً برای همین ساخته شده: هر توکن رنگی، فونت، فاصله‌گذاری و الگوی
کامپوننتی که همین الان توی پروژه‌ت داری، توش ثبت می‌شه و به ایجنت گفته می‌شه این
تنها واژگان بصری مجازه. اگه یه تسک نیاز به چیزی خارج از این فایل داشته باشه،
ایجنت موظفه اول پیشنهادش رو بده و منتظر تایید تو بمونه، نه اینکه خودسرانه یه
استایل جدید بسازه. این یعنی می‌تونی سرعت و ساختار رو بالا ببری بدون اینکه بعد از
چند تسک متوجه بشی ظاهر فروشگاه دیجیتال (Next.js 15 / RTL فارسی) عوض شده.

فایل `prompts/polish.md` هم یه چک‌لیست تایید بصری داره که آخر هر تسک اجرا می‌شه.

## نصب Graphify — فقط اگه پروژه بزرگه

اول از همه: `prompts/setup-interview.md` گام ۰ (تست اندازه پروژه، ۵ معیار
عینی) رو اجرا کن. اگه نتیجه‌ش **کوچیک** بود، از این بخش کلاً رد شو — `AGENTS.md`
بخش ۱ رو با `Graphify: no` تنظیم کن و همین. اگه **بزرگ** بود، ادامه بده.

⚠️ **هشدار بحرانی:** نام پکیج رسمی روی PyPI **`graphifyy`** با دو حرف `y` هست.

دستورات دقیق و به‌ترتیب (نصب → فعال‌سازی → خودکارسازی → ساخت گراف) رو به‌جای
تکرار اینجا، یه فایل جدا و مرتب ساختم: **`docs/GRAPHIFY-CHECKLIST-fa.md`** —
از بالا به پایینش رو دنبال کن، همین.

خروجی گراف سه فایله:

```
graphify-out/
├── graph.html       نمایش تعاملی در مرورگر
├── GRAPH_REPORT.md  خلاصه: God Nodes، ارتباطات غیرمنتظره، سوالات پیشنهادی
└── graph.json       گراف کامل — بدون نیاز به خوندن دوباره فایل‌ها قابل کوئری‌گیریه
```

بعد از مرحله ۴ چک‌لیست (`graphify hook install`)، آپدیت گراف بعد از هر کامیت
خودکاره — دیگه لازم نیست دستی `--update` بزنی.

### برای استفاده آینده از Claude در VSCode

وقتی به Claude Code رفتی و پروژه‌ت `Graphify: yes` بود، همون گراف قابل
استفاده‌ست — چک‌لیست مرحله ۷ رو ببین. چون از قبل `CLAUDE.md` رو داری (با
`@AGENTS.md` importش)، دستور نصب یه بخش مدیریت‌شده زیرش اضافه می‌کنه.

## چرخه توسعه پیشنهادی

```
Interview (فاز ۰)  ➔  Scaffold  ➔  API Layer  ➔  Hooks (منطق اشتراکی)  ➔  Components (UI)  ➔  Polish
```

هر فاز، فایل مربوطه توی `prompts/` رو می‌خونه. هیچ‌وقت فاز کدنویسی رو قبل از
تکمیل `edge.md` و `design.md` شروع نکن — و فاز Interview هم اول از همه تست
اندازه پروژه (گام ۰) رو انجام می‌ده، قبل از هر سوال دیگه‌ای.

## پیش‌شرط‌های اجرا (قبل از هر ران/کامیت)

```
tsc --noEmit
eslint .
```

این‌ها توی `AGENTS.md` بخش ۴ ثبت شدن تا ایجنت خودش قبل از هر بار اجرا چک کنه.

## چک‌لیست شروع پروژه

1. **Size Check:** گام ۰ توی `prompts/setup-interview.md` — نتیجه رو توی
   `AGENTS.md` بخش ۱ (`Graphify: yes/no`) ثبت کن
2. **Codify Rules:** پر کردن `edge.md`، `design.md`، و `roadmap.md` قبل از خط اول کد
3. **Automate Prompts:** استقرار `prompts/scaffold.md` و `prompts/polish.md`
4. **Initialize (فقط اگه Graphify: yes):** چک‌لیست کامل توی `docs/GRAPHIFY-CHECKLIST-fa.md`
5. **Iterative Polish:** اگه Graphify فعاله، با `graphify hook install` آپدیت
   گراف خودکار می‌شه؛ اگه نه، همین‌طوری جلو برو

## آیا برای پروژه‌های کوچیک هم لازمه؟

نه لزوماً — و این تصمیم الان یه تست رسمی داره، نه فقط حس کلی. توی
`prompts/setup-interview.md` گام ۰، ۵ معیار عینی رو می‌سنجه:

1. بیشتر از چند ساعت / بیشتر از یه نشست طول می‌کشه
2. حداقل ۳ ماژول/بخش جدا داره
3. توی چند سشن جدا کار روش می‌شه
4. بک‌اند/دیتابیس واقعی داره، نه فقط UI استاتیک
5. قراره در طول زمان فیچر بهش اضافه بشه

اگه ۳ یا بیشتر از این ۵ تا صادق بود → **بزرگ** → `Graphify: yes` →
`docs/GRAPHIFY-CHECKLIST-fa.md` رو دنبال کن.
اگه کمتر از ۳ بود → **کوچیک** → `Graphify: no` → کلاً نصبش نکن، فقط
`edge.md`/`design.md`/`roadmap.md` رو کوتاه پر کن.

این تست رو هم من الان می‌تونم روی توضیح پروژه‌ت اجرا کنم (همینجا بگو چیه)،
هم Claude توی Project چتت، هم خودِ OpenCode موقع فاز Interview — نتیجه‌ش
همیشه یکسانه چون معیارها ثابتن.

## چطور گیج نشیم که کِی چه دستوری باید بزنیم

این دقیقاً همون چیزیه که فایل `docs/COMMANDS-fa.md` براش ساخته شده — یه
چیت‌شیت که نشون می‌ده هر دستور کجا تایپ می‌شه (ترمینال یا چت) و کِی لازمه.
خلاصه‌ش: بعد از نصب اولیه، تقریباً هیچ‌وقت لازم نیست خودت دستور Graphify
بزنی — چون:

1. `AGENTS.md` به *ایجنت* می‌گه کِی گراف رو آپدیت کنه (نه به تو).
2. با یه‌بار زدن `graphify hook install`، گراف بعد از هر `git commit` خودش
   خودکار بازسازی می‌شه — بدون دخالت یا فراموشی تو.
3. تنها کاری که واقعاً دستی انجام می‌دی: پرامپت هر فاز رو توی چت OpenCode
   کپی-پیست می‌کنی — نگاه کن به `docs/PHASE-PROMPTS-fa.md`.

## ترتیب دقیق استفاده — از کجا شروع کنم؟

نیازی نیست فایلی رو دستی توی OpenCode «باز» کنی. وقتی OpenCode رو داخل پوشه
پروژه اجرا می‌کنی، خودش `AGENTS.md` رو اول سشن می‌خونه. تنها کاری که تو انجام
می‌دی اینه که پرامپت هر فاز رو توی چت بفرستی. متن آماده هر فاز (کپی-پیست) رو
گذاشتم توی `docs/PHASE-PROMPTS-fa.md` — ترتیبش:

```
۰. مصاحبه (تکمیل edge.md/design.md)  →  ۱. Scaffold  →  ۲. API Layer  →
۳. Hooks  →  ۴. Components  →  ۵. Polish
```

## «فاز کدنویسی رو قبل از تکمیل edge.md و design.md شروع نکن» یعنی چی؟

یعنی این دو فایل نباید با جای خالی (placeholder) بمونن. دو راه داری:

1. **دستی:** خودت بازشون کن و بخش‌های خالی رو با اطلاعات واقعی پروژه‌ت پر کن.
2. **با کمک ایجنت (پیشنهادی، ساده‌تر):** فایل جدید `prompts/setup-interview.md`
   رو اضافه کردم — دقیقاً برای همین. اولین پرامپتی که توی OpenCode می‌فرستی
   (فاز ۰ توی `PHASE-PROMPTS-fa.md`) به ایجنت می‌گه ازت سوال‌های کوتاه بپرسه،
   و اگه کد از قبل وجود داره، خودش از روی کد حدس بزنه و برای تایید نشونت بده.
   بعد از تایید تو، فایل‌ها پر می‌شن و تازه اونجاست که فاز Scaffold شروع می‌شه.

## آپدیت خودکار گراف

بله، کاملاً خودکار می‌شه. یه‌بار این رو بزن:

```bash
graphify hook install
```

از اون به بعد، بعد از هر کامیت گیت، گراف با تحلیل محلی AST (بدون هزینه API)
خودش بازسازی می‌شه. اگه وسط یه سشن طولانی هم می‌خوای زنده نگهش داری، توی یه
ترمینال جدا بزن:

```bash
graphify watch ./src
```

جزئیات کامل توی `docs/COMMANDS-fa.md`.

## آیا الگوی بهتری برای CLAUDE.md/GEMINI.md هست؟

آره — چک کردم، و الگوی فعلیت (یه فایل جدا با یه جمله‌ی راهنما) خوب بود ولی
یه سطح بهتر هم وجود داره که الان توی `CLAUDE.md` جایگزینش کردم:

**قبل:** `CLAUDE.md` یه توضیح متنی داشت («ببین AGENTS.md») که ایجنت *باید
تصمیم بگیره* بره بخونتش.

**الان:** خط اول `CLAUDE.md` شده `@AGENTS.md` — این سینتکس ایمپورت داخلی
خود Claude Code‌ه، یعنی تضمین‌شده محتوای `AGENTS.md` رو همون اول سشن بارگذاری
می‌کنه، نه اینکه صرفاً یه راهنمایی به ایجنت باشه. این الگو الان استاندارد
رایجیه که چندین منبع فنی به‌روز (بهار ۲۰۲۶) روش توافق دارن.

**یک لایه‌ی قوی‌تر هم هست** (اختیاری، برای وقتی با تیم کار کنی یا مطمئن باشی
روی مک/لینوکسی): به‌جای فایل جدا، یه symlink واقعی بساز که صفر درصد احتمال
واگرایی محتوا بمونه:

```bash
rm CLAUDE.md
ln -s AGENTS.md CLAUDE.md
```

⚠️ نکته: روی ویندوز این نیاز به فعال بودن Developer Mode یا تنظیم
`git config core.symlinks true` داره، وگرنه گیت symlink رو به‌صورت یه فایل
متنی معمولی (نه لینک واقعی) ذخیره می‌کنه. چون نمی‌دونم سیستم‌عاملت چیه، فعلاً
همون روش `@AGENTS.md` (بدون symlink) رو گذاشتم چون مستقل از سیستم‌عامل کار
می‌کنه — اگه مک/لینوکس داری و می‌خوای صفر تکرار، بگو تا این‌طوری تنظیمش کنم.

برای `GEMINI.md` سینتکس ایمپورت مشابهی به‌طور قطعی مستند نشده؛ یه گزینه‌ست
که توی `.gemini/settings.json` مستقیماً بگی Gemini CLI اسم فایل کانتکستش
`AGENTS.md` باشه (و کلاً `GEMINI.md` رو حذف کنی) — ولی چون معلوم نیست از
Gemini CLI به‌طور فعال استفاده می‌کنی یا از Google AI Studio، همون پوینتر
ساده رو نگه داشتم؛ اگه بعداً سراغ Gemini CLI رفتی بگو تا این‌طوری آپدیتش کنم.

## بهترین شیوه‌ی فعلی — آیا چیز بهتری هست؟

دو تا لایه‌ی جدا از هم داریم که هرکدوم رو جدا باید سنجید:

- **لایه‌ی فایل دستورالعمل (AGENTS.md):** این الان واقعاً به یه استاندارد
  عرفی صنعتی تبدیل شده — یه فرمت باز که زیر نظر Agentic AI Foundation (Linux
  Foundation) نگهداری می‌شه و بیش از ۶۰ هزار پروژه اوپن‌سورس و ۳۰+ ابزار
  (از جمله OpenCode، Codex، Cursor، Gemini CLI) ازش استفاده می‌کنن. چیزی که
  ساختیم دقیقاً همینه، پس از این نظر چیز «بهتری» فعلاً وجود نداره.
- **لایه‌ی edge.md/design.md/prompts (روش Graphify):** این یه متدولوژی خوب
  و عملیه که از منابعی که گذاشتی گرفتیم، ولی خودش یه استاندارد رسمی صنعتی
  نیست — یه لایه‌ی مهندسی‌شده‌ی خوب روی بالای AGENTS.md‌ه. برای پروژه یه‌نفره
  مثل الان تو، این ترکیب (AGENTS.md استاندارد + لایه‌ی قوانین Graphify) دقیقاً
  همون چیزیه که تیم‌های حرفه‌ای هم همین الان دارن جمعش می‌کنن؛ چیز رده‌بالاتری
  (مثل گراف دانش تیمی/سرور MCP اشتراکی) عملاً مخصوص تیم‌های چندنفره‌ست و برای
  الان اضافه‌ست.

## یک نکته درباره برچسب‌های اعتماد (Confidence Tags)

هر رابطه‌ای که گراف گزارش می‌ده یکی از این سه برچسب رو داره:

- `EXTRACTED` — مستقیم از کد استخراج شده، قابل اعتماد
- `INFERRED` — با منطق graphify استنتاج شده، معمولاً درسته ولی برای چیزای حساس
  (حذف، مایگریشن، منطق احراز هویت) قبل از اقدام تاییدش کن
- `AMBIGUOUS` — نیاز به بررسی انسانی داره، خودسرانه روش عمل نکن

---

با این ساختار، مدل‌های رایگان (مثل Gemini 2.0 Flash روی OpenCode) هم می‌تونن با
داشتن نقشه دقیق پروژه، خروجی نزدیک به مدل‌های گران‌قیمت تولید کنن — چون کمبود
پارامتر مدل با ساختاردهی دقیق دانش جبران می‌شه.

## افزایش قدرت استدلال خام مدل‌های رایگان

صادقانه بگم: وزن‌های یه مدل رو نمی‌شه واقعاً «قوی‌تر» کرد — ولی چند اهرم واقعی
هست که فاصله‌ی عملی رو کم می‌کنه:

1. **انتخاب مدل رایگان قوی‌تر:** همه‌ی مدل‌های «رایگان» هم‌سطح نیستن. تا همین
   الان (جولای ۲۰۲۶) خانواده‌های GLM، Kimi K2، DeepSeek و Qwen روی استدلال و
   کدنویسی عامل‌محور به مدل‌های تجاری بسته خیلی نزدیک شدن. اگه از طریق
   OpenRouter یا مشابهش به مدل‌های رایگان دسترسی داری، دنبال نسخه‌های
   «thinking» یا «reasoning» این خانواده‌ها بگرد — چون این نسخه‌ها مشخصاً برای
   زنجیره استدلال آموزش دیدن، نه فقط تولید متن. (دسترسی رایگان به هرکدوم بسته
   به پروایدر عوض می‌شه، پس لیست فعلی رایگان‌ها رو خودت چک کن.)
2. **وادار کردن به فکر گام‌به‌گام:** همین الان توی `AGENTS.md` بخش ۸ (Reasoning
   Discipline) اضافه‌ش کردم — قبل از جواب نهایی، مدل رو مجبور می‌کنه مسئله رو
   مرحله‌به‌مرحله جلو ببره، نه اینکه مستقیم بپره سراغ جواب.
3. **مقایسه چند رویکرد قبل از تصمیم برگشت‌ناپذیر:** برای هر تصمیم حساس (تغییر
   schema، منطق احراز هویت)، از مدل بخواه حداقل دو رویکرد رو کنار هم بذاره و
   بعد انتخاب کنه — این هم توی همون بخش ۸ ثبت شده.
4. **خرد کردن مسئله:** خود چرخه‌ی Scaffold→API→Hooks→Components→Polish این کارو
   می‌کنه — هرچی تسک ریزتر و مشخص‌تر باشه، بار استدلالی کمتری روی دوش مدل
   می‌مونه. این از هر تکنیک پرامپت‌نویسی مؤثرتره.
5. **قضاوت رو بسپار به ابزار قطعی، نه حدس مدل:** `tsc`/`eslint` (بخش ۴
   `AGENTS.md`) دقیقاً همینه — به‌جای اینکه مدل حدس بزنه کد درسته یا نه، یه
   ابزار قطعی جواب می‌ده.
6. **بازبینی مستقل بعد از تولید:** بخش ۸ همچنین از مدل می‌خواد بعد از نوشتن کد،
   یه‌بار دیگه مثل یه ریویوئر مستقل بهش نگاه کنه و دنبال ایراد بگرده — این
   تکنیک reflection نامیده می‌شه و برای مدل‌های ضعیف‌تر تفاوت واقعی ایجاد می‌کنه.

## وادار کردن مدل به درخواست کمک از Claude رایگان، فقط جایی که واقعاً لازمه

فایل جدید `prompts/escalate.md` رو دقیقاً برای همین اضافه کردم. منطقش:

- به‌جای معیارهای مبهم («اگه مطمئن نیستی...»)، شرط‌های عینی و قابل‌شمارش تعریف
  کردم — چون مدل‌های ضعیف‌تر دقیقاً در همون «تشخیص اینکه گیر کردن» ضعیف‌ترن، پس
  یه معیار قابل‌شمارش (نه یه قضاوت ذهنی از خودش) قابل‌اعتمادتره.
- شروط توقف: دوبار تلاش ناموفق برای رفع یه خطای مشخص، هر تصمیم معماری
  برگشت‌ناپذیر که توی `edge.md` قفل نشده، هر چیزی که به پرداخت/احراز هویت
  مربوطه (بدون استثنا)، رابطه‌ی `AMBIGUOUS` قبل از یه اقدام مخرب، یا یه تغییر
  که چند فایل رو هم‌زمان درگیر می‌کنه و پیامدهاش روشن نیست.
- وقتی یکی از این شرطا فعال بشه، مدل باید: متوقف بشه، دلیلش رو کوتاه بگه، و یه
  **پرامپت آماده و خودکفا** برات بسازه که مستقیم توی Claude رایگان پیست کنی —
  فقط شامل زمینه‌ی لازم (نه کل فایل‌ها، برای صرفه‌جویی توی سهمیه پیام رایگانت)،
  و از Claude می‌خواد یه **تصمیم یا تشخیص** بده، نه کل پیاده‌سازی — پیاده‌سازی
  واقعی بعداً توی OpenCode انجام می‌شه.
- بعد از گرفتن جواب از Claude، مدل صبر می‌کنه تا تو جوابش رو پیستش کنی، و
  خودسرانه ادامه نمی‌ده.

⚠️ یه نکته‌ی صادقانه: این یه دستورالعمل بهترین‌تلاشه (best-effort)، نه یه
تضمین صددرصدی — هر مدلی، حتی قوی‌ترینا، این‌جور قوانین رو به‌صورت احتمالی
دنبال می‌کنن نه قطعی. ولی چون شروط بالا عینی و قابل‌شمارشن (نه «اگه حس کردی
سخته»)، احتمال رعایتشون خیلی بیشتر از یه قانون کلیه.
